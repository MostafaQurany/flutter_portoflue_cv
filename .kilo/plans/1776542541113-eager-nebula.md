# Portfolio Cleanup And Preview Crash Fix Plan

## Goal
Rebuild the project cleanup plan to match the current `.kilo` configuration in `kilo.json`, the active architect agent guidance, and the added skills, while fixing the preview/runtime crash caused by broken asset loading in the projects feature.

## Active `.kilo` Constraints
- `kilo.json` sets `default_agent` to `flutter_architect` and prefers `analyze` plus `run-web` as the main verification commands.
- The active rule file is `.kilo/rules/project-rules.md`.
- The active skills are:
  - `feature-generator.md`
  - `widget-splitter.md`
  - `wasm-auditor.md`
- The project rules now require:
  - feature-first clean architecture
  - Riverpod 3.0 for data binding
  - Signals 6.0 for surgical UI updates where needed
  - macro-first modeling instead of generated `.g.dart` or `.freezed.dart` files
  - atomic design separation for UI
  - Wasm-safe UI code and no `dart:io` in UI layers
  - const-first widget construction

## Findings
- The codebase already uses a partial feature-first layout under `lib/features/*` and central cross-cutting code under `lib/core/*`.
- `lib/features/projects/presentation/pages/project_details_screen.dart` is still far too large and directly violates the current widget-splitting direction from `.kilo/skills/widget-splitter.md`.
- `lib/features/projects/presentation/widgets/projects_section.dart` combines section composition, card rendering, image rendering, and link launching, which should be split into smaller atomic pieces.
- `assets/data/projects.json` contains asset keys like `assets/images/logos/wasla_logo.png`.
- The immediate preview/runtime bug is in `_ProjectImage` inside `lib/features/projects/presentation/widgets/projects_section.dart`.
- `_ProjectImage` removes the `assets/` prefix before calling `Image.asset`, so valid asset keys from JSON are turned into invalid runtime keys such as `images/logos/wasla_logo.png`.
- On Flutter Web, this becomes the exact 404 pattern the user reported.
- `pubspec.yaml` already registers `assets/images/`, so the root issue is incorrect asset key handling, not asset registration.
- There may still be missing physical asset files in `assets/images/logos/`; that must be verified during implementation after correcting the asset key handling.
- Current project rules in `.kilo/rules/project-rules.md` describe a target structure with `core/design_system/` and optional `shared/`, so the previous plan should avoid introducing a conflicting top-level `lib/app/` move unless it is strictly necessary.

## Plan Corrections From The Previous Version
- Remove the assumption that `lib/app.dart` must be moved to `lib/app/portfolio_app.dart`.
- Keep the app shell stable unless a move is needed for clarity after the crash fix.
- Align widget decomposition with the `widget-splitter` skill:
  - atoms in `lib/core/design_system/atoms`
  - molecules in `lib/core/design_system/molecules`
  - feature-specific organisms in feature presentation widgets
- Include a Wasm audit step because `wasm-auditor.md` is now part of the active skill set.
- Keep the plan additive and minimal rather than broad structural churn.

## Change Classification
- Asset crash fix: Type B, modifies runtime behavior but preserves public contracts.
- Widget splitting and folder cleanup: Type A, additive organization cleanup within existing feature boundaries.
- Any introduction of Signals into existing providers: Type B and optional only if a specific UI hotspot benefits from surgical updates.

## Implementation Plan
1. Fix the preview/runtime crash first.
   - Update the local asset branch in `_ProjectImage` so `Image.asset` receives the original full asset key.
   - Keep network image loading unchanged.
   - Preserve graceful fallback UI through `errorBuilder`.

2. Verify asset reality after the path fix.
   - Check that the logo files referenced in `assets/data/projects.json` actually exist.
   - If files are missing, either align JSON paths to real files or keep the fallback visible without breaking the app preview.
   - Do not change `pubspec.yaml` unless a real registration gap is found.

3. Apply the `widget-splitter` skill to project presentation files.
   - Split `project_details_screen.dart` into page plus smaller focused widgets.
   - Split `projects_section.dart` into section, grid, card hero, image, and action widgets.
   - Keep the page file responsible only for route input, provider state handling, and top-level layout assembly.

4. Introduce atomic design where it clearly reduces duplication.
   - Promote generic fallback/image-chip/info-card primitives into `core/design_system/atoms` or `molecules`.
   - Keep project-specific layouts inside `features/projects/presentation/widgets`.
   - Avoid over-abstracting one-off visuals.

5. Respect the current state-management direction.
   - Preserve Riverpod providers already in place.
   - Only add Signals if a specific subtree needs fine-grained updates; do not force a migration without measurable benefit.
   - Keep business logic out of widgets and move any non-trivial UI decision logic into providers or dedicated helpers if needed.

6. Run a Wasm compatibility audit during cleanup.
   - Confirm no `dart:io`, `dart:html`, or `dart:js` leaks into UI/shared code touched by the refactor.
   - Ensure image/loading helpers remain web-safe.
   - Avoid introducing JS-only patterns while addressing preview behavior.

7. Preserve architecture and route behavior.
   - Keep current `GoRouter` paths unchanged.
   - Preserve admin guard behavior in `core/routing/app_router.dart`.
   - Avoid unnecessary moves of app bootstrap files unless implementation shows a concrete readability benefit.

8. Validate according to `kilo.json` preferred commands.
   - Run `flutter analyze`.
   - Run the web preview flow and verify the projects list and details screen no longer fail on valid local assets.
   - Check that all newly extracted widgets use `const` where possible.

## Implementation Boundaries
- In scope:
  - project asset loading fix
  - project presentation widget decomposition
  - atomic design extraction for clear reusable UI pieces
  - Wasm-safety audit for touched files
- Out of scope:
  - backend or API changes
  - adding new packages unless absolutely required
  - broad migration to Signals across unrelated features
  - redesigning routing or admin auth behavior

## Risks
- Some logos referenced by JSON may truly not exist, which would still produce fallback rendering after the path bug is fixed.
- Large-file splitting can accidentally change visual spacing or animation behavior if extracted too aggressively.
- Over-applying atomic design can create unnecessary indirection; extraction should only happen where reuse or readability clearly improves.

## Acceptance Criteria
- The preview/runtime asset 404 caused by incorrect local asset key handling is resolved.
- Project cards and project details render valid local assets correctly on web.
- Missing assets degrade gracefully through fallback UI instead of breaking preview behavior.
- `project_details_screen.dart` and `projects_section.dart` are decomposed into smaller, focused widgets.
- The resulting structure aligns with the active `.kilo` rules, especially feature-first organization, atomic design, const usage, and Wasm-safe UI code.
- `flutter analyze` passes cleanly.
- The web run path remains stable under the `run-web` workflow.

## Notes For Execution
- Fix the asset bug before any structural changes.
- Prefer minimal safe moves over ambitious folder churn.
- Only introduce new atoms and molecules when they reduce duplication or clarify responsibility.
- Treat Signals as optional optimization, not a mandatory migration step for this task.
